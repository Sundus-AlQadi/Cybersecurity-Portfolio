# Lab 08: Brute-Forcing a Stay-Logged-In Cookie

## Platform

PortSwigger Web Security Academy

## Difficulty

Practitioner

## Topic

Authentication Vulnerabilities / Remember-Me Cookies / Brute Force / Encoding and Hashing

## Lab Status

Solved

## Objective

The goal of this lab was to brute-force a vulnerable stay-logged-in cookie and access the victim user's account page in a controlled lab environment.

## Simple Explanation

The application allowed users to stay logged in by setting a persistent cookie.

However, the cookie was created in a predictable way. After decoding the cookie, it was possible to understand that it contained the username and an MD5 hash of the user's password.

The cookie format was:

```text
base64(username + ":" + md5(password))
```

Because the victim username was known and a candidate password list was provided, it was possible to generate possible cookie values and test them until the correct cookie was found.

## Vulnerability Description

The application was vulnerable because the stay-logged-in cookie was not random or securely generated.

Instead, it was based on predictable user information:

* The username
* An MD5 hash of the password
* Base64 encoding

Base64 is not encryption. It only converts data into another format. MD5 is also not suitable for secure password protection because it is fast and can be brute-forced.

This allowed the remember-me cookie to be brute-forced using Burp Intruder payload processing.

## Key Concept

Remember-me cookies should be random, high-entropy tokens generated by the server.

They should not be created from predictable values such as usernames and password hashes.

## Steps Taken

1. Opened the lab from PortSwigger Web Security Academy.
2. Logged in using the provided personal credentials.
3. Selected the `Stay logged in` option.
4. Captured the request containing the stay-logged-in cookie using Burp Suite.
5. Decoded the cookie using Base64 decoding.
6. Observed that the decoded cookie contained a username and a hash value.
7. Identified that the hash matched an MD5 hash of the user's password.
8. Confirmed that the cookie format followed this structure:

```text
base64(username + ":" + md5(password))
```

9. Sent the `GET /my-account` request to Burp Intruder.
10. Added a payload position to the stay-logged-in cookie value.
11. Tested the payload processing rules using the known personal password.
12. Added payload processing rules in this order:

    * Hash the payload using MD5
    * Add the username prefix
    * Base64-encode the final value
13. Added a Grep-Match rule for `Update email` to identify successful account access.
14. Confirmed that the generated cookie worked for the personal account.
15. Changed the account ID parameter to target the victim user.
16. Changed the payload prefix to the victim username.
17. Loaded the candidate password list.
18. Started the Intruder attack.
19. Identified the successful response by finding the response that contained `Update email`.
20. Accessed the victim user's account page.
21. The lab was successfully solved.

## Result

The victim user's stay-logged-in cookie was successfully brute-forced.

The successful response was identified by the presence of the `Update email` button, which indicated access to the account page.

## What I Learned

* Remember-me cookies must be securely generated.
* Base64 encoding is not encryption.
* MD5 hashes are fast and weak for password-based security.
* Predictable cookie formats can lead to account takeover.
* Burp Intruder payload processing can be used to transform payloads before sending requests.
* Grep-Match can help identify successful authentication responses.

## Security Impact

In a real-world application, this vulnerability could allow attackers to generate valid remember-me cookies for other users if usernames are known and passwords can be guessed.

This may lead to unauthorized account access without needing to log in through the normal authentication form.

## Mitigation

To prevent this vulnerability, developers should:

* Use random, server-generated remember-me tokens.
* Store remember-me tokens securely on the server side.
* Avoid including usernames or password hashes inside cookies.
* Avoid using MD5 for password-related security.
* Use secure password hashing algorithms for passwords.
* Set secure cookie attributes such as `HttpOnly`, `Secure`, and `SameSite`.
* Rotate and expire remember-me tokens.
* Invalidate tokens after logout or password change.
* Monitor suspicious repeated cookie attempts.
